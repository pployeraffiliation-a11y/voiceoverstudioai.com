## Batch vs streaming : la vraie décision

La plupart des workflows API tombent dans l’une de ces deux catégories.

**Batch**

- cours
- narration longue
- bibliothèques doublées
- exports récurrents

**Streaming**

- guidance produit
- assistants
- IVR
- interactions UI rapides

Le mauvais choix vient souvent d’une obsession du “temps réel” trop tôt.

## Commencer plus petit qu’on ne le pense

Un setup API stable démarre souvent avec :

- une voix
- un seul schéma d’endpoint
- une seule structure de prompt
- une convention de nommage

Si vous introduisez trop de variables d’un coup, le debug devient plus difficile que la génération.

## La cohérence vocale compte plus que la nouveauté technique

Le vrai problème d’un setup API n’est souvent pas la latence. C’est la dérive :

- même prompt, rendu différent
- même voix, rythme différent
- même phrase, prononciation différente

C’est pour cela que la discipline de prompt et le contrôle du glossaire comptent avant l’échelle.

## Ajouter cache et logs tôt

Si vous générez des phrases répétées, mettez-les en cache.

Si une même ligne sonne faux deux fois, loguez-la.

Si un membre de l’équipe change une règle de prompt, documentez-le.

Ces petites habitudes évitent le classique “c’était mieux la semaine dernière”.

## Quand l’API doit attendre

L’API ne doit pas être votre premier mouvement si :

- l’équipe réécrit encore les prompts en permanence
- le glossaire n’est pas stable
- personne ne possède la QA
- le format de contenu change chaque semaine

Dans ce cas, il faut d’abord stabiliser l’éditorial avant de scaler techniquement.
